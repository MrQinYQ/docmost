# git-delivery：Git 交付与已关联文档发布

日期：2026-10-16。状态：用户已确认规格，待实现计划审阅；本文件描述拟实现行为，不代表功能已经可用或验收通过。

## 目标和已确认要求

创建可复用的 `git-delivery` Skill，支持暂存、生成合理提交信息、提交、推送，以及推送后合并到用户指定的测试/main 等分支并推送目标分支。

任意分支成功提交后，检查已关联项目 Markdown 的变化并发布到原 Docmost 页面，再同步到原有知识库目标。不同分支共用同一页面；分支内容冲突时暂停，不创建分支副本。提交后即发布，不以 push 成功或 main 分支作为前提。

Skill 在用户要求 Git 交付时串联操作，确定性的 Git 快照读取、发布基线、条件更新、持久化任务和知识库同步由程序执行。普通终端、IDE 或其他工具自行执行的 commit/push 不会被这个 Skill 自动监听。

成功标准：Git 各阶段结果可核对；发布内容属于准确的提交；未提交内容不外发；分支分叉和远端编辑不会被静默覆盖；Docmost、知识库和 Git 的完成状态分别报告；失败后可继续处理而不重复成功写入。

## 现有实现与需要补充的能力

- 当前 `bind_markdown` 读取工作区文件，后续保存触发整页条件更新。它没有 Git 提交对象和分支发布基线，不能直接当作提交发布入口。
- 当前 `sync_page_to_knowledge` 读取 Docmost 已保存全文，适用于已有页面入库；它不负责项目文件到页面的关联，也不提供普通正文修改的条件写入。
- fork 的 `/api/pages/sync-state`、`/api/pages/sync-update` 可校验实时协作版本并条件替换。新增 Git 发布必须复用此协议，不退回普通 `update_page` 来绕过冲突保护。
- 当前私有账本、页面租约、确认快照、知识库任务及个人/共享目标保护可复用。新增来源需要与已有来源互斥，而不是另外维护一条可能重复写入同页的通道。

## Git 交付流程

### 指令决定操作范围

| 用户要求 | 执行范围 |
| --- | --- |
| 提交修改 | 检查、必要验证、暂存、生成提交信息、commit、发布相关文档。 |
| 提交并推送 | 提交流程，再推送指定/已配置远端和分支。 |
| 只推送已有提交 | 推送已有提交，并核对已关联文档和未完成任务；不制造新提交。 |
| 提交、推送并合并到目标分支 | 提交和源分支推送，核对目标状态，合并到明确指定的目标，检查合并结果并发布文档，推送目标。 |

目标分支由本次指令或项目明确配置确定，不把测试分支名硬编码为 `test`，也不自行推断要合并 main。目标不明确时仅询问缺少的目标信息，继续完成不依赖该信息的已授权步骤。

检查已有暂存区、工作区、新增/删除文件、当前分支、远端及合并状态。按照本次任务范围暂存；用户明确说“全部修改”时包含修改、新增和删除。已有暂存内容要纳入范围核对，不能静默混入无关改动。

提交信息依据实际 diff 和项目既有规范生成，描述最终修改目的。只有存在可独立解释和验证的变更时才拆分提交，不按文件机械拆分。分别验证每个真实提交结果，不把 Git 命令超时当作提交失败后直接重做。

合并遇到冲突时保留现场、说明受影响文件；按用户已授权的合并目标处理可确定的冲突，无法确定业务取舍时暂停该合并阶段。不得以删除本地修改、强制推送或改写无关历史作为常规流程。

### 发布时机

每个由 Skill 创建的成功提交后立即尝试文档发布，即使后面尚未 push。快速前进合并没有新 commit，也需要检查目标最终提交；产生合并提交时读取合并后的最终树。仅检查到中间暂存状态不构成发布依据。

已关联文件内容相同则跳过正文写入。没有新的文档变化时仍检查未完成的知识库任务，允许补处理。所有发布均记录完整 commit 对象 ID、调用时的分支及是否已确认推送；未推送提交不生成声称可访问的远端源码链接。

文档冲突或知识库失败不回滚 Git 提交，也不取消已明确授权且不依赖文档结果的后续 Git 步骤。最终报告各阶段的成功、暂停、失败与待处理项。用户明确要求“文档发布成功后才能继续”时，该条件成为后续步骤的门槛。

## 配置、关联和来源互斥

Git 交付功能本身不要求安装 Docmost。没有文档同步配置时正常完成 Git 流程，并报告文档同步未启用。

Docmost Git 发布使用新增的可选 `DOCMOST_GIT_ROOT`，指向一个明确允许读取的现有 Git 工作树绝对路径。版本一每个 MCP 连接允许一个 Git 根；其他项目可配置独立连接。链接工作树通过规范化的 Git common directory 确认同一仓库身份，不能因文件同名或远端名称相似自动继承关联。

私有发布状态复用 `DOCMOST_KNOWLEDGE_STATE_DIR`，或已有的 `DOCMOST_SYNC_STATE_DIR`。同一 MCP 连接的 Git、MD 和页面来源必须使用同一私有账本，避免同页多写入者。状态目录位于源目录之外，保留现有 0700/0600、所有者、非符号链接和租约约束。不在 Git 仓库内保存会话、Key、业务正文快照或私有状态。

每条关联记录仓库身份、相对 `.md` 路径、固定 Docmost 部署/用户/工作区/页面/空间，以及明确选择的知识库目标。所有分支使用这条关联和同一页面。Git 路径不决定 Docmost 目录；知识库继续使用 Docmost 空间及完整父页层级，不新增分支目录。

“以前上传过”必须转化为明确关联：已有账本能证明来源时复用；只有同名页面不能自动关联。首次 Git 关联不创建页面、不覆盖正文，核对指定提交的规范化正文与 Docmost 实时及持久化正文的一致性后建立基线。不一致时先展示差异，等待用户选定/合并内容。

同页只允许一个正文来源。已有保存自动同步或页面来源转为 Git 来源时，必须通过显式模式转换，保留同一页面和知识库目标；先对账旧任务和未知提交结果，再关闭原来源的自动行为。存在不确定写入或活跃租约时拒绝转换。转换不是创建第二条记录，也不能直接编辑私有 JSON 绕过检查。

知识库仍为可选适配层。只更新原关联中已选择的知识库目标；不为 Git 发布偷偷启用 OpenViking、切换个人/共享范围或补建其他镜像。

## 指定提交的不可变快照

新增 Git 读取模块使用参数数组执行 Git，不拼接 shell。工具输入解析为完整 commit 对象 ID，再从该提交的 tree/blob 读取正文；不读取 index 或工作区最新文件作为发布内容。调用前校验分支 ref 指向请求的提交，执行期间固定对象 ID，不随分支移动改变正文。

只处理显式关联的普通 UTF-8 `.md` blob，沿用 1,000,000 字节和非空正文限制。拒绝目录、符号链接、submodule、路径越界及非法对象。文件名以 NUL 分隔读取，路径参数和修订参数分离，支持合法的中文、空格等文件名，不允许路径或分支名触发选项/命令注入。

Skill 可显示本次新增/修改/删除文档清单，但未关联文档不自动上传，不自动建页。重命名检测仅提供候选；仅在原路径消失且目标唯一、内容一致时更新路径关联；其余重命名需要用户确认原关联的新路径。相对路径改变不自动修改页面标题或 Docmost 目录。

本地文件删除时暂停该关联并报告待处理，不删除 Docmost 页面或知识库原文。明确要求删除远端时继续使用既有 Docmost 删除流程及其知识库清理规则。

## 同一页面的分支冲突规则

每条关联保存最近一次已确认发布的 Git commit、blob/正文哈希及 Docmost 实时版本基线。Git 正文哈希与 Docmost 条件版本分别保存，不能互相当作 CAS 令牌。

候选提交的处理顺序：

1. 先对账上一笔未确认操作；结果未知时不发起下一次正文更新。
2. 候选 blob 与已确认发布正文相同时不重写正文，也不将发布基线倒退到旧提交；仍核对 Docmost 实时和持久化版本。远端未偏离基线时更新检查结果并补知识库任务，已偏离时报告冲突，不将旧版本说成当前文档。
3. 正文有变化时，上次已发布 commit 必须是候选 commit 的祖先。不是祖先即报告分支冲突并暂停。第一版采用保守规则，不代替用户做跨分支文本合并。
4. 本地缺少已发布 commit 对象时报告历史不足；不把浅克隆、对象缺失当成“没有冲突”。按已授权 Git 流程补齐历史后再检查。
5. 再核对 Docmost 实时版本与已确认基线，并通过服务器 CAS 条件更新。网页或其他客户端修改时暂停，即使 Git 历史连续也不能覆盖。

分支冲突的正常解决方式是在 Git 合并/rebase 后产生包含已发布提交的新提交，再显式重新发布。Docmost 侧冲突由用户选择保留/合并内容，并提供刚读取的远端版本进行显式条件解决。简单恢复任务不能重置基线或推导覆盖授权。

这保证 dev A 已发布后，基于旧版本的 dev B 不能仅因“更新发生得更晚”就覆盖 A。合并到测试/main 后正文相同则跳过，合并产生新的全文则重新校验并发布。

## 发布协调与状态

在 MCP 中新增 Git 关联、指定提交批量发布、状态读取、来源管理及显式冲突解决入口。实现计划会列出具体 schema；这些是本次要新增的接口，不是现有工具能力。

Git 状态至少区分：未关联、无正文变化、待发布、发布中、分支冲突、Docmost 冲突、结果待确认、源文件删除、部署不支持、已确认。知识库沿用独立的排队/处理/失败/已同步状态，不能因为 Git 或 Docmost 成功就报告知识库完成。

派发前持久化准确的提交、正文快照、预期远端版本和目标。确认实时与持久化正文达到本次版本后推进发布基线，再处理知识库；知识库使用该次确认快照，不能替换成之后的工作区正文。

失败恢复复用现有任务对账原则：网络中断后先查询结果，不能盲目重发；知识库重试不重复 Docmost 写入；目标身份、根或关联模式变化时不改投旧任务。同一页面沿用统一租约，暂停和 MCP 退出不派发新任务，已提交服务端任务允许下次启动只读对账。

## Skill 内容与交付文件

版本化源码位于 `skills/git-delivery/`：

- `SKILL.md`：触发范围、Git 操作模式、提交信息、每次提交后文档发布和分阶段报告。
- `agents/openai.yaml`：与真实能力一致的中文说明及默认提示，保持默认自动发现。
- `references/document-sync.md`：关联设置、任意分支共页规则、冲突处理、状态及自验步骤。
- 必要的只读 Git 检查辅助脚本：生成准确的 Git 状态/提交文档清单。提交信息的语义判断保留给 Agent；正文发布机制放在 MCP，避免脚本私自读凭据或绕过 MCP。

更新 Docmost Skill 的相关入口，说明 Git 发布和保存自动同步的互斥关系。通用 Git Skill 无文档配置时不加载 Docmost 细节，也不要求知识库在线。

通过验证后将同版本 `git-delivery` 安装到本机可发现的 Skill 目录，保留其他 Skill 和客户端设置。此次实现任务不包含把实际项目改动提交或推送到 GitHub；验收中的 commit/push/merge 仅作用于独立测试仓库。

## 验证与真实验收

先在隔离场景运行无 Skill 的行为基线，再用完成的 Skill 执行相同交付请求，检查暂存范围、提交信息、分支发布、冲突暂停、失败补处理和结果报告。脚本、Git 读取、账本与 MCP 工具使用有意义的回归测试；稳定后集中运行完整受影响测试。

真实验收使用专用本地 Git 工作仓库和 bare 远端，执行真实 add/commit/push/merge/push，并从 bare 远端核对最终对象 ID。这验证 Git 操作及文件传输远端，不声称覆盖 GitHub 网络认证或分支保护。

Docmost 使用本机 fork 的真实个人会话、条件同步接口和专用页面；OpenViking 使用既有获授权连接和专用测试资源。全部正文为新建合成测试内容，不修改已有业务文档、不清空个人或共享资源根、不使用 `ov` 命令。公司部署若缺条件同步接口，只能报告不支持，不能用本机验收宣称公司可安全自动上传。

验收至少覆盖：

1. 无 Docmost 配置时完成合理暂存、提交信息生成及真实 Git 推送。
2. feature 分支提交已关联文档，push 前即更新同一 Docmost 页面和知识库全文。
3. 提交后保留额外未提交修改，证明远端只有提交版本；未关联新 MD 不创建页面。
4. 第二个从旧基线分出的分支修改同文档，发布暂停，页面和知识库保留已发布版本；页面 UUID 和总数证明未建分支副本。
5. Git 合并后再次发布成功；相同正文合并到测试/main 不重复正文写入，目标 bare 分支对象 ID 正确。
6. 网页协作修改后提交本地文档，CAS 拒绝覆盖；明确合并解决后继续。
7. 知识库阶段失败后，Git 和 Docmost 成功结果保留；恢复后仅补知识库，完整原文、摘要/向量任务及限定检索分别核对。
8. 改名保留页面身份；删除本地 MD 不自动删除远端；MCP 重启能对账未完成任务。
9. 个人/共享配置和已有 MD、页面链路回归，确保没有因为新来源破坏原有行为。

结束时通过授权的 MCP 删除本次专用页面和所拥有的测试镜像，核对无测试残留。私有原文、会话及报告位于 ignored 目录或仓库外私有目录；公开测试使用合成数据。交付说明分别列出自动测试、真实 Git/Docmost/OpenViking 证据和未覆盖的环境限制。

## 本轮不包含

Git hooks、CI 或常驻监听；自动给未关联文档建页；分支副本；任意二进制附件发布；知识库回写仓库；自动复制 Docmost ACL；自动发布整个工作区；强推或历史清理；绕过缺失条件接口的公司部署。
